## What AEGIS is

A WhatsApp-native autonomous agent for Google's "All Things Agentic
Hackathon" (Taskmaster track): it investigates forwarded scam
messages/images/audio, verifies them against a shared anonymized threat
database, and takes protective action (plain-language reply, report
draft, opt-in family notification) — with real asynchronous re-engagement
hours later, not just a chat loop.

Hard requirements it must satisfy: Gemini (3.5+) via Vertex AI, Google
ADK for agent orchestration, at least one GCP infra service (uses Cloud
Run, Pub/Sub, Firestore, KMS, Cloud Scheduler, Secret Manager), real
background async processing, a working deploy + architecture diagram.

## Two important architectural decisions to preserve

1. Contact directory (why a "hash everything" system can still reply on
   WhatsApp): user_id = HMAC-SHA256(wa_id, AEGIS_USER_ID_PEPPER)
   everywhere (Firestore keys, logs, reasoning trace) — one-way, by
   design. But AEGIS has to message people, so the raw wa_id rides one
   hop (ingestion -> orchestrator, never logged) and gets KMS-encrypted
   into user_directory/{user_id}.encrypted_wa_id. Decrypted in exactly
   one place, whatsapp_sender.py, right before the Graph API call —
   never inside a tool function (would leak into the logged reasoning
   trace). See README "Contact-directory design".

2. Async follow-ups are Firestore-backed, not just Pub/Sub, because
   Pub/Sub can't delay delivery. escalate_or_close("monitor") writes a
   `follow_ups` doc with `not_before`; the Cloud Scheduler-triggered Job
   queries for due ones. This is what makes "runs asynchronously in the
   background" literally true.

## Bugs already found and fixed — do not reintroduce these

- Every Firestore write MUST use `.model_dump(mode="python")`, never
  `mode="json"`. json-mode serializes datetimes to ISO strings, and
  Firestore silently excludes a string field from a `<=` range query
  against a datetime value — this broke `due_follow_ups()` completely
  (found via a real Firestore emulator, not a mock).
- The orchestrator's Cloud Run env + Secret Manager IAM must include
  AEGIS_USER_ID_PEPPER (family_link_commands.py needs it to hash a
  phone number the same way ingestion does) — this was missing and
  would have crashed the first LINK FAMILY command in production.
- Pub/Sub's and Cloud Scheduler's own service agents need
  `roles/iam.serviceAccountTokenCreator` granted on the pubsub_invoker /
  scheduler_invoker service accounts respectively (see iam.tf) — without
  it, `terraform apply` succeeds but the push subscription / scheduled
  job silently fail to authenticate forever afterward, with no error
  pointing at why.
- `google_billing_budget.budget_filter.projects` wants
  `projects/{numeric project NUMBER}`, not the project ID string — use
  `data.google_project.current.number`.
- Any new Firestore query needs a genuine Firestore-emulator test if it
  uses a range/inequality filter — mocked unit tests will not catch a
  serialization mismatch like the one above. Pattern already established
  in services/*/tests/test_firestore_integration.py.
- Never pass a key named `args` (or `msg`, `message`, `asctime`, or any
  other reserved LogRecord attribute) in a `logger.X(..., extra={...})`
  call — it raises `KeyError` at log time, but ONLY once logging is
  actually enabled at INFO+ (pytest's root logger defaults to WARNING,
  so this is invisible under the normal test suite). Found via
  `_before_tool_callback`'s `extra={"args": ...}` — fixed to
  `"tool_args"`. Regression test:
  services/agent-orchestrator/tests/test_agent_callbacks_logging.py,
  which explicitly forces INFO via `caplog.at_level` — copy that pattern
  for any other logger.info/warning/error extra= dict you add.

## The next day, the full loop completed -- and found one more real bug

Same demo, same key, next day: the full 6-call chain (analyze_content ->
check_sender_reputation x2 -> cross_reference_reports x2 ->
draft_protective_action -> escalate_or_close -> finish_task) completed
with a 200. The model correctly classified the test message (verdict:
scam, confidence 1.0, patterns urgency + credential_phishing) and wrote a
genuinely good plain-language explanation + report draft -- but the
Firestore doc read back with verdict: None and only a 4-step reasoning
trace, not the full run.

Bug: `escalate_or_close`'s write only means to set
{report_id, user_id, status}, but `upsert_user_report` dumped the WHOLE
UserReportDoc (every other field at its Python default: None, []), and
Firestore's merge=True still overwrites a field if it's PRESENT in the
payload regardless of whether it's a real value or just a default --
so each partial status update silently nulled out the verdict/
confidence/reasoning_trace a PREVIOUS call (draft_protective_action) had
just written. Exactly the kind of bug that only shows up when multiple
partial writes to the same doc happen in sequence -- unit-testing each
Firestore function in isolation never catches it.

Fixed: `model_dump(mode="python", exclude_unset=True)` in both
agent-orchestrator's `upsert_user_report` and followup-worker's
`upsert_user_report_status` -- a partial update now only touches fields
its caller explicitly set. Confirmed by reverting the fix and watching
`test_later_partial_upsert_does_not_clobber_earlier_verdict_and_trace`
fail with the exact real symptom, then reapplying and re-running the
whole live demo: final Firestore state now shows the correct verdict,
both drafts, and the complete 17-step reasoning trace intact.

**Do not remove `exclude_unset=True` from either of those two functions.**
If you add a new partial-update call site against `user_reports`, make
sure the `UserReportDoc(...)` you construct only explicitly passes the
fields you actually mean to change -- anything else falls back to
`exclude_unset` correctly leaving it alone, but only if you don't
explicitly pass it as `None`/default on purpose.
