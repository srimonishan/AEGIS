## What AEGIS is

AEGIS is a WhatsApp-native autonomous scam-protection agent for Google's
"All Things Agentic Hackathon" Taskmaster track. It receives forwarded
messages/images/audio, runs them through guardrails, analyzes them with a
Gemini-backed Google ADK agent, cross-checks shared anonymized threat
memory, replies in plain language, drafts a report, optionally notifies a
family contact, and schedules asynchronous follow-up checks.

Hackathon requirements this project is designed to satisfy:

- Gemini via Vertex AI in the production configuration.
- Google ADK for agent orchestration.
- Real GCP infrastructure, not a local-only demo: Cloud Run, Pub/Sub,
  Firestore, Cloud KMS, Cloud Scheduler, Secret Manager, Terraform.
- Background async work via Cloud Scheduler + Cloud Run Job + Firestore
  due-records.
- Architecture diagram, dashboard, and deploy instructions.

## Stack

- Python services: FastAPI, Pydantic shared schemas, `google-adk==2.7.1`.
- AI: Gemini through ADK; production env is Vertex AI
  (`GOOGLE_GENAI_USE_VERTEXAI=true`), while some live development runs
  used the Gemini Developer API with `GOOGLE_API_KEY`.
- Data and infra: Pub/Sub, Firestore, KMS, Secret Manager, Cloud Run,
  Cloud Run Jobs, Cloud Scheduler, Terraform provider `hashicorp/google`.
- WhatsApp Graph API version: configured by Terraform through
  `meta_graph_api_version`, defaulting to `v25.0`.
- Dashboard: React + Vite + Tailwind + Firebase Auth.
- CI: `.github/workflows/ci.yml`.

## What is built

- Shared Pydantic schemas for Pub/Sub events and Firestore documents.
- Guardrail pipeline: PII redaction, injection heuristics, prompt wrapper
  with `<untrusted_forwarded_content>`.
- Ingestion service: Meta webhook verification, payload normalization,
  media handling, Pub/Sub publishing.
- Agent orchestrator: ADK agent with five tools:
  `analyze_content`, `check_sender_reputation`,
  `cross_reference_reports`, `draft_protective_action`,
  `escalate_or_close`.
- Deterministic command handlers before any model call:
  `family_link_commands.py` and `data_deletion_commands.py`.
- Contact directory: raw WhatsApp ID is only kept encrypted with KMS in
  `user_directory` and decrypted only right before WhatsApp send.
- Follow-up worker: scheduled job queries due Firestore `follow_ups`
  documents and escalates, reschedules, or closes.
- Dashboard: live feed, pattern map, case drilldown, Firebase Auth gate.
- Terraform: Pub/Sub, Firestore, KMS, Secret Manager, IAM, Cloud Run,
  Cloud Run Job, Scheduler, monitoring alerts, budget, remote state.
- Real-number configuration: `meta_phone_number_id` selects the sending
  WhatsApp Business phone number, `meta_graph_api_version` pins the
  versioned Graph API path, and `aegis-meta-access-token` must be

- CI covering Python tests, dashboard build, Docker builds, Terraform

## Architectural invariants to preserve

1. Every model call must pass through guardrails. The orchestrator
   sanitizes initial content and also uses `before_model_callback`.

2. User-forwarded content is adversarial data. Do not let text inside a
   forwarded scam message act as an instruction to the agent.

3. Family-link and data-deletion commands are deliberately not ADK tools.
   They use exact command grammars before guardrails or Gemini so a scam
   message cannot trick the model into linking a third party or deleting
   data.

4. `user_id = HMAC-SHA256(wa_id, AEGIS_USER_ID_PEPPER)` everywhere
   except the encrypted contact directory. Raw WhatsApp numbers must not
   enter tool arguments, reasoning traces, logs, or dashboard documents.

5. Async follow-up is Firestore-backed. Pub/Sub cannot delay delivery, so
   `escalate_or_close(decision="monitor")` must write `follow_ups` with
   `not_before`, and the scheduled worker must query due records.

6. Firestore writes that persist datetimes must use
   `model_dump(mode="python")`, not `mode="json"`.

7. Partial updates to `user_reports` must not clobber prior fields.
   Preserve `exclude_unset=True` in:
   - `services/agent-orchestrator/firestore_client.py::upsert_user_report`
   - `services/followup-worker/firestore_client.py::upsert_user_report_status`

8. Do not use reserved `logging.LogRecord` keys in `extra={...}`. In
   particular avoid `args`, `msg`, `message`, and `asctime`; use names
   like `tool_args`.

9. Any new Firestore range/inequality query needs a real Firestore
   emulator test. Mocked tests missed the datetime serialization bug.

## Bugs already found and fixed

- `model_dump(mode="json")` serialized datetimes to strings, causing
  Firestore range queries to silently miss due follow-ups. Fixed with
  `mode="python"` and emulator tests.
- Missing `AEGIS_USER_ID_PEPPER` in orchestrator Cloud Run config would
  have broken `LINK FAMILY`. Fixed in Terraform.
- Pub/Sub and Cloud Scheduler service agents needed
  `roles/iam.serviceAccountTokenCreator` on their invoker service
  accounts. Fixed in IAM.
- `google_billing_budget.budget_filter.projects` needs the numeric
  project number, not project ID. Fixed via `data.google_project.current`.
- `logger.info(..., extra={"args": ...})` raised `KeyError` only when
  INFO logging was enabled. Fixed to `tool_args` and covered by a
  regression test.
- Later partial Firestore updates nulled earlier verdict/confidence/trace
  fields. Fixed with `exclude_unset=True` and regression-tested via a
  real Firestore emulator.

## Deployment notes

`terraform.tfvars` is intentionally ignored. Secret values must not go in
Terraform variables or state. Terraform creates Secret Manager containers
and IAM; secret versions are added out-of-band:

```bash
echo -n "your-meta-app-secret"     | gcloud secrets versions add aegis-meta-app-secret --data-file=-
echo -n "your-verify-token"        | gcloud secrets versions add aegis-meta-verify-token --data-file=-
echo -n "your-meta-access-token"   | gcloud secrets versions add aegis-meta-access-token --data-file=-
echo -n "$AEGIS_USER_ID_PEPPER"    | gcloud secrets versions add aegis-user-id-pepper --data-file=-
echo -n "$GLOBAL_PATTERN_SALT"     | gcloud secrets versions add aegis-global-pattern-salt --data-file=-
```

Cloud Run reads secret versions at container start, so after adding new
secret versions you need a new Cloud Run revision.
